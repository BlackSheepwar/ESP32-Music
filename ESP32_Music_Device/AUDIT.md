## 1. 严重缺陷（全部已修）

### S1 · `KS_Synth_Init` 与渲染并发 → 空指针 / 除零崩溃 ✅ 已修

**问题**：`KS_Synth_Init()` 的第一件事是 `memset(s, 0, sizeof(*s))`，把 **66KB** 的合成器对象整个清零。
而它原本在**按键任务**（`task_key_cmd`）里被调用，同时**音频任务**可能正在对**同一个对象**跑 `KS_Synth_Render()`。

| 崩溃点 | 机理 |
|---|---|
| 空指针解引用 | `memset` 在 offset 0 就把 `music` 清成 NULL，而渲染路径会解引用 `s->music->...` → `LoadProhibited` |
| 除零 panic | `memset` 推进到 `step_samples` 时它短暂为 0，而渲染里做 `s->frame / s->step_samples` |

**真实触发路径**（不是理论）：

```
① 曾成功上传过一次（s_has_audio = 1）
② 按 KEY1 开始录音；录音期间按一下 KEY2 → 走"有音频"分支把 PLAY 入队
③ KEY1 松手 → 开始上传（原本在这一步才调 KS_Synth_Init）
④ 音频任务处理完录音后立刻继续 PLAY（因为 RECORD_START 原先不清 s_playing）
   → 音乐在上传期间自己响，合成器正在被渲染
⑤ 上传结束 → KS_Synth_Init 去 memset 一个正在被渲染的对象 → 崩溃/爆音
```

**修法**：把「初始化合成器」改成一条**命令**（`AUDIO_CMD_SYNTH_RELOAD`），
由音频任务执行，调用方通过信号量等回执。合成器对象的所有权变为唯一。

- 新增 `App_Audio_SynthReload(void *synth, void *music)`（`app_audio.c`）
- `app_music_app.c` 改为调它，**不再**直接调 `KS_Synth_Init()`
- 用 `void*` 传参，保持 `APP_AUDIO` 不依赖 `Middlewares` 组件（分层约定）

### S2 · `pick_position == 0.5` → 整首曲子完全静音 ✅ 已修

**问题**：后端 `music.js:250` 里 **harp 的 `pick_position` 正好是 `0.50`**。

```
d_samples = pick_pos × 2 × n = 0.5 × 2 × n = n   （恰好是整数）
→ i1 = i − n，环回后 i1 == i 自身
→ delayed = buf[i]
→ buf[i] -= buf[i] = 0        ← 整条激励被清零
→ peak = 0，又跳过归一化 → 永久静音
```

因为 `pick_pos` 是**全局参数**，所以**旋律 + 低音 + 和弦全部没声 —— 整首歌一点声音都没有**。

**修法**（三处，形成防线）：

1. 边界检查：`if (d_samples >= 1.0f && d_samples < (float)v->n - 0.5f)`
2. `KS_Synth_Init` 里上限从 `0.5` 收到 `0.49`
3. `peak < 1e-6` 时重新填白噪声兜底，**绝不静音**

> 参考实现 `esp32-music/worker/src/demo-page.js:677` 同样用 `pickPos < 0.5` 排除，
> 固件漏了这个边界。

### S3 · `loop=1` 实际不循环：放完一遍就永久静音 ✅ 已修

**问题**：`music_synth_fill()` 无条件 `return n`（恒 > 0），于是播放任务里处理
"音源结束"的分支**永远不可达** → 循环重绕是死代码。

结果：第 128 步之后不再触发新音，已有声部约 2 秒衰减完，之后是纯数字静音，
而 `s_playing` 仍是 1。

**修法**：两个条件都满足才算一轮结束，`fill` 返回 `-1`：

```c
if (KS_Synth_IsFinished(s_synth) && KS_Synth_ActiveVoices(s_synth) == 0)
    return -1;
```

第二个条件不能省：`decay_seconds` 最长 3.5 秒，若还有声部在响就重绕，
`KS_Synth_Restart` 会把所有声部置 FREE（等于硬切）→ 循环接缝处"咔"一声。

- 新增 `KS_Synth_ActiveVoices()`
- **依赖 S4 的修复**：否则声部永不回收，`ActiveVoices` 恒为 32，条件永不成立

### S4 · 声部 `amp` 从不衰减 → 声部池永不回收 ✅ 已修

**问题**：`ks_voice_next()` 里 `v->amp` **只被读、从不写** —— 它是**静态增益**
（和弦 0.45 / 低音 0.90 / 旋律 0.75），从拨弦到结束都不变；衰减发生在延迟线内部
（`buf[]` 逐圈乘 `d`）。

于是回收条件 `voice->amp < 1e-5f` **永远不成立**（是死代码），后果：

1. 32 个声部槽很快占满且永不释放 → 之后每次拨弦都在**抢占**：
   用新噪声整条覆盖 `buf[]` → 从上一音的任意相位跳到新激励 → **每抢占一次一声"咔"**
2. 抢占目标是 `amp` 最小者，而 `amp` 与剩余能量无关 → 经常把刚拨响、最响的声部切掉
3. 32 个声部永远 ACTIVE → 内层循环永远跑满 32 次 → **CPU 常驻满负荷**

**修法**：给声部加 `life` / `life_max`，上限取 `decay_seconds`（衰减到 −60dB）+ 100ms
余量，在混音循环里按寿命回收。语义上正好等于"这个音已经听不见了"。

### S5 · `strum` 永远解析成 0 → 扫弦退化成"根音连弹" ✅ 已修

**问题**：后端 `music.js:792` 返回的 `strum` 是 **JSON 布尔**，而固件用
`music_get_int()`（依赖 `cJSON_IsNumber`）去读。

ESP-IDF 绑定的 cJSON 里 `cJSON_True`（`1<<1`）与 `cJSON_Number`（`1<<3`）
是**不同的位** → `IsNumber` 对布尔返回 false → **永远取到 fallback 0**。

后果：后端要给"扫弦"时会同时给 `arp_pattern = [0,0,0,0]`（`music.js:284`），
固件走普通音型分支 → `tone = 0 % count = 0` → **每一格都拨同一个根音** ——
正是 `music.js:726-728` 注释里说"听着很怪"、后端已经修掉的那个行为。

**修法**：新增 `music_get_bool_int()`（`cJSON_IsBool` + `cJSON_IsTrue`，
兼容 1/0 数字写法）。

### S6 · `chord_notes[base + tone]` 越界 → 可致 ±2MB 偏移崩溃 ✅ 已修

**问题**：`chord_notes` 的读取偏移完全由后端下发的 `chord_note_counts` 前缀和决定，
而 `music_get_int_array()` **只保证写入端不越界**（`written < cap`），**完全不校验元素值**。
`chord_notes_len`（实际写入长度）在 `ks_synth.c` 里**一次都没被使用**。

触发条件包括**完全合法的输入**：

| 输入 | 后果 |
|---|---|
| 32 小节 × 每小节 7 个和弦音 = 224 > 192 | 越界读 |
| `chord_notes` 项数 > 192 时静默截断，而 counts 照单全收 | 越界读 |
| 畸形响应给 32767 / −1 → 前缀和达 ±100 万 | 地址偏移 ±2MB → `LoadProhibited` |

**修法**（双保险）：

1. 解析器里逐小节夹到"剩余可用和弦音数"之内，负值归零
2. KS 侧用 `chord_count[]` 本地副本（`chord_offset[b] + chord_count[b] <= 192` 恒成立）
3. `ks_trigger_step()` 里 `bar` 在**索引任何数组之前**就查边界
   （原写法只在最后读 `bass_notes` 时才检查，顺序是错的）

### S7 · 整数字段无范围校验 + `(int16_t)` 截断 ✅ 已修

**问题**：cJSON 对超范围数字会饱和成 `INT_MAX`/`INT_MIN`，直接 `(int16_t)` 转换
会截断成任意值（如 `1e30 → INT_MAX → -1`）。而 `step_ms` / `beats_per_bar` /
`steps_per_beat` 都会进入时间轴乘法 —— 负值会造成 `(uint32_t)(负 double)` 的未定义行为。

**修法**：新增 `music_clamp_int()` / `music_clamp_float()`（NaN 也要挡掉，
否则比较全为 false 会让 NaN 直接进入 `powf` 并发散），逐字段 clamp。

## 2.5 修复过程中自己引入的 P0 缺陷（★ 必读 ★）

**审计修复本身也会引入新缺陷。** 本轮就发生了一次，而且差点让整条上传链路失效。

### P0 · `s_synth_done` / `s_synth_lock` 从未被创建

**我做了什么**：为解决 S1（合成器跨任务 `memset`），新增了两个信号量
`s_synth_done`（回执）和 `s_synth_lock`（会话锁），并在 `App_Audio_Init()` 里
插入创建代码。

**实际结果**：那次插入的**字符串替换没有匹配上**，我看到了"未匹配"的提示，
**但没有回头验证**。于是这两个符号只有声明和使用、没有创建。

**后果链**（逐环都成立）：

```
App_Audio_SynthReload() 的 NULL 守卫恒真 → 立即 return -1
  → AUDIO_CMD_SYNTH_RELOAD 命令永远发不出去 → 音频任务里那个分支不可达
  → KS_Synth_Init 永不执行 → s_has_audio 永远为 0
  → task_key.c 的返回码 switch 里 APP_MUSIC_ERR_PARSE 落到 default
  → 串口打印「上传失败：网络/后端问题」
```

**用户可见症状**：上传明明 **HTTP 200 成功**，设备却报"上传失败：网络/后端问题"，
之后 KEY2 永远说"没有可播放音频"。

**这个 bug 最恶劣的地方**：它**伪装成网络问题** —— 而网络问题正是本工程
绕了两圈的坑（见 `HARDWARE.md §3.2`）。如果没抓到，下一次排查会又去查 DNS、
查域名、查代理。

**为什么编译器不报警**：拿指针和 `NULL` 比较是合法 C，`-Wall -Wextra -Werror=all` 都不报。

**是谁发现的**：对抗性复核（专门安排一个通道去"找我的错"，而不是确认我做对了）。

**修法**：在 `App_Audio_Init()` 里真的创建它们。用 `xSemaphoreCreateMutex()`
而不是 `xSemaphoreCreateBinary()` —— 因为 binary 的初始 count 是 0，
创建后必须补一次 `xSemaphoreGive` 才能 take，很容易漏。

**顺带修掉的关联问题**：`task_key.c` 的返回码 `switch` 原来没有
`APP_MUSIC_ERR_PARSE` 分支，所以"后端已响应但解析失败"会和"网络失败"
报同一句话。现在分开报，并给出两个具体排查方向。

### 从这次事故得到的四条工程纪律

1. **批量替换后必须回读文件确认改动落地**，不能只看替换语句有没有报错。
   本次 `grep` 一下 `xSemaphoreCreate` 就能立刻发现 —— 成本 5 秒。
2. **"改完编译通过"不等于"改对了"**。这个 bug 编译零警告、链接正常、
   固件能跑、WiFi 能连、探活能成功 —— 只有真正按 KEY1 才会暴露。
3. **对抗性复核必须安排**。让一个独立通道专门去找"我引入的错"，
   而不是让它确认我做得对。本次它找到的 P0 是我自己三次检查都没发现的。
4. **错误信息必须区分层次**。"网络失败"和"解析失败"报同一句话，
   会把排查方向带偏 —— 这正是本工程已经踩过两次的坑。

## 2.6 修复过程中自己引入的第二个缺陷：按键"第二次按没反应"

### 现象（用户实测报告）

> 「第一次按 KEY1 能正确录音并上传，**第二次就无法录音了**」
>
> 日志里还有一串：`W APP_KEY: event queue full, drop key2 evt=1 (total drop 7)`

### 根因：为省日志，丢掉了状态转换事件

我为了消除上传期间刷屏的 `event queue full` 告警，加了一个"消费者忙就丢弃新事件"的
标志。**这个方向从根本上是错的** —— 因为本模块**没有任何周期性重复事件**：

```
APP_KEY_STATE_NO   --按下消抖稳定--> DOWN    --> YES
APP_KEY_STATE_YES  --释放消抖稳定--> CLICK   --> NO
APP_KEY_STATE_YES  --长按超时-----> LONG    --> LONG
APP_KEY_STATE_LONG --释放--------> LONG_UP --> NO
```

四种事件**全部是状态机的唯一次机会**，丢掉任何一个都会让按键状态与上层记录
永久不一致（上层不会自己恢复）。

**完整故障链**：

```
t=33.3s  按 KEY1 → DOWN → s_key1_recording = 1，开始录音
t=36.5s  松手 → 但此时【上一次录音的上传】还没结束
         → 忙标志把 CLICK（松手）事件丢弃  ❌
         → s_key1_recording 永远停在 1、录音永远不停
之后     再按 KEY1 → DOWN → App_Audio_RecordStart 被拒（已在录音中）
         → 上层什么都不打印 → 【第二次按 KEY1 完全没反应】
```

我用第二版"只丢重复事件"去修，一查枚举就发现**行不通**（没有重复事件）。

### 真正的解法：别让消费者长时间不消费

问题的本质不是"事件太多"，而是**上传阻塞按键任务 45 秒 ~ 3.75 分钟**，
而队列只有 16 深 —— 溢出是必然的。

所以把上传**搬到独立的 worker 任务**（`Task_Key_Upload`）：

| | 改动前 | 改动后 |
|---|---|---|
| 谁执行上传 | `Task_Key_Cmd`（同步，最坏 3.75 分钟） | `Task_Key_Upload`（独立任务） |
| `Task_Key_Cmd` 做什么 | 干完整条上传链路 | 只投一条信号量（微秒级），立刻回去消费事件 |
| 事件队列 | 必然溢出 → 丢状态转换事件 | 正常消费，不会溢出 |
| 重复上传请求 | 排队，结果是两次上传同一份音频 | `s_upload_busy` 拒绝，并明确提示用户 |

新增栈 `STACK_KEY_UPLOAD 8192`（上传要跑 TLS 握手 + `cJSON_Parse` + 合成器初始化）。

### 这次事故的教训（比上一次更值得记）

**上一次（P0 信号量）是"改了但没落地"；这一次是"改对了地方但改错了方向"。**
两次的共同点是：**我为了解决一个次要问题（日志刷屏 / 一个报错），
动到了核心状态机，却没有先把状态机的完整语义读清楚。**

具体到可执行的纪律：

1. **动事件/状态机之前，先把它的全部状态与转换列出来。**
   本次只要提前看一眼 `app_key.c` 顶部的状态图，就会立刻发现"没有可丢的事件"。
2. **"抑制"类优化必须证明被抑制的东西是幂等的或可重建的。**
   按键的松手事件既非幂等也非可重建 —— 丢了就永远丢了。
3. **次要问题（日志刷屏）不配用核心机制的改动去换。**
   正确做法是改日志策略（降级/限流），或者像最终方案那样
   从根上消除阻塞（搬任务），而不是动事件投递。
4. **用户报的"第一次能用第二次不能用"这类描述，优先怀疑状态残留**，
   而不是"功能坏了"。对称的可用→不可用转换，几乎总是某个标志没被清。

## 2.7 修复过程中自己引入的第三个缺陷：**所有闪烁图案全部失效**

### 现象（用户实测报告）

> 「连接的热点我把手机热点关了这个指示灯还是亮着」
> 「真的完全常亮，一点闪都没有」

### 排查过程（值得记录，因为方向错过很多次）

我先按"WiFi 逻辑"查了一整轮：BSP 事件注册、`Notify` 条件、状态机判断、图案定义、
引脚映射 —— **全部正确**。用户提供的带诊断日志证实了这一点：

```
W BSP_WIFI: STA: disconnected, raw reason=1 (OTHER)       ← 断连检测到了
I APP_WIFI: BSP 事件: state=3 reason=6 (当前 CONNECTED)    ← 事件送到了
I APP_WIFI: state: CONNECTED -> RETRY_WAIT                ← 状态机切换了
```

**状态机切到 `RETRY_WAIT` 就必然调 `app_wifi_led(&APP_LED_PAT_SLOW_BLINK)`
→ `App_LED_Set(APP_LED_WIFI, SLOW_BLINK)`。** 所以矛盾是：
状态机说"设成慢闪了"，物理上却完全不闪。

**于是把 LED 模块单独编到 PC 上跑**（`tools/led_test.c`），一次就复现：

```
=== 测试 3：常亮 → 慢闪 ===
  Set(SLOW_BLINK) 立刻写入硬件 1 次
  4 秒内翻转 0 次                    ← 修复前
  ✗ FAIL: SLOW_BLINK 必须产生电平翻转
```

### 根因：电平判断被写了两份，互相吃掉结果

`app_led_advance_locked()` 末尾原来是：

```c
uint8_t idx  = app_led_step_to_index(p, inst->step);
uint8_t want = (idx == 0xFF) ? 0 : ((idx & 1) ? 0 : 1);

if (want == level_before)
    return 0;
inst->level = want;      /* ← 它自己把 level 改成新值了 */
return 1;
```

而调用方 `App_LED_Service()`：

```c
if (app_led_advance_locked(inst))     /* 内部已经把 level 改成新值 */
    app_led_apply_locked(inst);        /* 再比一次：on == level → 不写 GPIO */
```

**`advance` 抢先把 `level` 更新掉，`apply` 一比较"没变"，于是永远不写硬件。**

| 图案 | 为什么"看起来正常" |
|---|---|
| `PAT_ON` / `PAT_OFF` | 被 `advance` 开头的早退拦住（`len==0` 或 `steps[0]==0`），`level` 交给 `apply` 写 → 正常 |
| **所有闪烁图案** | `advance` 每 tick 都在内部改 `level`，`apply` 永远检测不到变化 → **冻结** |

**唯一在闪的是生命灯** —— 因为它走 `App_LED_HeartbeatToggle()`，由独立任务直接翻 GPIO，
**不经过图案引擎**。所以之前一直没暴露。

### 修法：职责单一

- `app_led_advance_locked()`：**只推进 `step` / `elapsed_ms`（纯相位），完全不碰 `level`**
- `app_led_apply_locked()`：算目标电平 + 比较 + 写 GPIO（**唯一**碰 `level` 的地方）

修复后（`tools/run_led_test.ps1`）：

```
4 秒内翻转 5 次                    ✅
断线重连全过程翻转 27 次            ✅
```

### 这个 bug 是我"审计修复 M1"时引入的

M1 原本的问题是"锁内改状态、锁外写 GPIO"，会因过期快照让灯永久停错。
我当时把 `apply` 也挪进锁内 —— 但同时**在 `advance` 里重复实现了一遍电平判断**，
两份判断共享同一个 `level` 变量，后一个就把前一个的结果吃掉了。

**教训一**：**同一份状态不要在两个地方各写一遍判断逻辑。**
正确做法是先定义清楚"谁拥有 `level`"，再让另一个函数只读不写。

**教训二**：`PAT_ON` / `PAT_OFF` 正常会让人误以为"引擎没问题"。
**验证一个机制时必须覆盖它的全部分支** —— 静态图案和动态图案是两条路径。

**教训三**：**"模块能在真机上跑"不等于"它的每个分支都验证过"。**
这个 bug 在真机上表现为一个完全误导人的现象（WiFi 断了灯不闪），
把排查方向引到 WiFi 状态机上；而在 PC 上单独驱动那个模块，
**一次测试就定位了**。这就是"能不能离线验证"的价值。

### 已建立回归测试

`tools/led_test.c` + `tools/run_led_test.ps1`（9 项断言）把它钉住了：
常亮不翻转、**慢闪必须翻转**、断线全过程必须大量翻转、常灭要灭灯、生命灯独立翻转。

### M1 细节：为什么"锁外写 GPIO"会让灯永久停错

```
T1(Service, core1)                     T2(App_LED_Set, core0)
─────────────────────────────────     ────────────────────────
锁内算出 want=0，level=0，出锁
                                      锁内 pattern=ON, level=0xFF，出锁
                                      apply → level=1, GPIO=HIGH
用【过期的快照 level=0】写 GPIO=LOW
→ 池里说 pattern=ON/level=1，实际灯是灭的
→ 之后对"常亮"图案 advance 直接 return（不再写硬件）
→ 【永久停在错误状态】，直到下一次图案切换
```

**修法**：把「推进相位 + 比较电平 + 写 GPIO」全部放进**同一个临界区**。
前提已核对：ESP-IDF 5.4.4 的 `gpio_set_level()` 就是 `gpio_hal_set_level()`
**直写寄存器、内部不取任何锁**，所以在自旋锁里调用它不会死锁。

### M3 细节：为什么不能用 `xQueueReset` 实现"停止"

`App_Audio_Stop()` 原本是「先 `xQueueReset` 清空整个命令队列，再压入 STOP」。
但队列里可能正排着 `RECORD_START`：

```
KEY2 循环播放中 → 按 KEY1（入队 [STOP, REC_START]）→ 250ms 内再按 KEY2
→ 走"停止播放"分支 → xQueueReset 把 [STOP, REC_START] 一起清掉
→ 录音从未开始，但录音灯已点亮
→ 松手时 s_recording 还是 0 → RecordStop 走早退分支 → 返回上一轮帧数
→ 上层看到 ≥0.5 秒 → 继续上传 → 【上传上一轮的旧音频】
```

**修法**：用**世代号**（`s_play_gen` / `s_rec_gen`）替代。丢弃的是"过期请求"，
而不是"队列里所有命令"。录音类命令**永远不丢**。

## 4. 已知限制（记录在案，未修）

### L1 · 音高偏低最多 −82 音分（分数延迟补偿方式）

**现状**：一阶低通同时承担「高频阻尼」和「分数延迟补偿」，取
`a = max(a_damp, a_frac)`。而环路总延迟 = `n + τ(a)`，`n` 只取 `floor(fs/f)`，
**没有把 τ 扣掉**。只要 `a_damp > a_frac`（中高音几乎总是），环路就偏长 → 音偏低。

实测最差偏差（16kHz，MIDI 36..84）：

| 音色 | damping | 最差偏差 |
|---|---|---|
| nylon_guitar | 0.38 | −40.7 音分 |
| clean_electric | 0.46 | −60.6 |
| bass_pluck | 0.53 | **−81.9** |
| harp | 0.24 | −14.1 |

**正确修法**：先从延迟线长度里扣掉 `τ`，再另用一阶全通补 `frac`
（参考实现 `demo-page.js:647-661` 就是这样，实测偏差 < 0.6 音分）。
代价：改最热的 `ks_voice_next()`、每声部加 3 个 float。

**为什么暂缓**：属于听感调优，不影响功能正确性；且扬声器尚未到货，无法听测验证。

### L2 · `damping` 强依赖采样率（16kHz 下阻尼强 3~7 倍）

后端 `music.js:243-252` 的数值是在**浏览器 48kHz** 上听感调出来的。
同一个 `a`，`fs` 从 48k 降到 16k 时 `ω0` 变 3 倍 → `|H|` 显著变小。

实测 −60dB 时间：nylon MIDI72 **492ms(16k) vs 1490ms(48k)**；
clean MIDI84 55ms vs 385ms。→ demo 里 C6 还有半秒余音，固件里 80ms 就没了。

**修法**：`a_16 = a_48^(48/16) = a_48³`（一行 `powf`）。
同样等扬声器到货后一起调。

### L3 · 未实现的契约细节

- `strum_spread_ms = 22`（`music.js:793`）：契约要求各弦错开 22ms，
  固件用"递减音量"近似。要做对需在 synths 里加小事件队列 `{at_frame, midi, amp}`
- `melody_hold` 完全没用。**当前无问题**：后端 `hold ∈ {1,2}`、最慢 `step_ms=68ms`
  → 最长 136ms ≪ 最短音色 banjo 的 1.0s 衰减
- 鼓点字段已解析但未合成（`MUSIC_MAX_DRUM_STEPS` 因此偏大，无害）

### L4 · `MUSIC_MAX_MELODY_STEPS = 256` 只在 4/4-八分音符下够

后端 `beats_per_bar` 可到 8、`steps_per_beat` 到 4 → 理论 32×32 = 1024。
**今天不可达**：LLM 的 schema 里没有这两个字段，`clampInt(undefined,2,8,4)`
恒为 4、`steps_per_beat` 恒为 2 → `steps_per_bar` 恒为 8 → melody 恰好 256。
若后端将来放开这两个字段，需把上限提到 512 或加一致性校验。

---

### L4 · 锁的粒度：临界区里有一段 PSRAM `memcpy`

`audio_do_record()` 里 1KB 的 `memcpy`（录音缓冲在 PSRAM）在自旋锁内，
期间另一核会自旋等待约**十几微秒**。

**为什么这么写**：录音数据流是「音频任务写、按键任务读打包 WAV」，
必须让「写缓冲」这件事对读者原子。锁内定范围 + 锁内拷贝是最直接的实现。

**更好的做法**（如果以后发现这十几微秒有影响）：
「锁内定范围 → 锁外拷贝 → 锁内发布长度」。这样锁内只剩几条赋值。
当前没有任何可观测影响，所以保持简单。

> 另外：M9 修复后，探活拿不到锁会**立即跳过**（不再等 70 秒），
> 所以「探活长时间占锁把按键任务钉住」这个问题已经消除。
> 现在只有上传会长时间持锁，而上传本来就该独占后端访问权。

**审计期间发现的元问题**：多个审计通道**同时读取**一份正在被修改的代码树，
导致它们报告的行号来自不同快照。所以本文档中所有结论都以「函数名 + 代码片段」
定位，而非行号 —— 这也是为什么修复时逐条重新核实过（`read` + `grep`），
而不是直接照搬报告。

**最关键的一条经验**：审计报告的结论**必须独立复核**。
本次有 2 条报告结论在我复核后判定为**误报**：

- 「`BSP\CMakeLists.txt` 缺 `BSP_WIFI`」—— 实为我自己的 grep 过滤器把带右括号的行滤掉了
- 「`KS_MidiToFreq` 声明无实现」—— 实为头文件里的 `static inline`

反之，**S1（合成器跨任务 memset）和 S2（harp 静音）是我自己没发现的真实缺陷**，
子代理找到后我逐条核实并复现了推导过程 —— 其中 S2 还通过离线测试
（harp `rms=0.05905`）得到了最终确认。
